# Предлагаемая архитектура

Статус: согласованная основа; initial implementation готова, ожидается кроссплатформенная CI-проверка.  
Архитектурная цель: один Python-код для Windows и Linux, с отделением UI, домена, хранилища, сетевых источников данных и платформенных адаптеров.

## Границы слоёв

- **UI (`ui/`)** — минимальное окно ожидания, внешний оверлей и диалоги настроек на PySide6 Widgets. Не обращается к SQLite или сети напрямую.
- **Домен (`domain/`)** — простые модели, перечисления, правила проверки и доменные ошибки. Не зависит от PySide6 и платформы.
- **Сервисы (`services/`)** — сценарии работы с каталогом и единой локальной подборкой, обнаружением Steam, локализацией и необязательными публичными данными. Старые profile tables и репозиторий сохраняются только для чтения/миграции уже созданных данных.
- **Хранилище (`storage/`)** — SQLite, версии схемы, транзакции и репозитории. Соединение создаётся в composition root и передаётся явно.
- **Адаптеры (`adapters/`)** — интерфейсы и реализации для определения платформы, чтения метаданных, внешних источников и симуляции операций с ресурсами. Адаптер ресурсов в первом этапе только симулирует операции.
- **Конфигурация и запуск** — `app.py`, `config.py`, `logging_setup.py`; связывают зависимости, но не содержат бизнес-правила.

Ошибки переводятся в понятные пользовательские сообщения на границе сервис/UI; технические детали остаются в безопасном журнале. Медленный файловый, сетевой или импортный ввод-вывод выполняется вне GUI-потока с отменой для длительных задач.

## Направление зависимостей

```text
UI → services → domain
             ↘ storage interfaces / repositories
             ↘ adapter interfaces
composition root → конкретные адаптеры, SQLite, Qt UI
```

Доменные модели не импортируют UI и платформенные модули. Сервисы получают зависимости через конструкторы/фабрики, без глобального изменяемого состояния. Steam detection реализуется платформенным интерфейсом и возвращает кандидаты путей с уровнем уверенности; сканирование только читает файлы конфигурации Steam и не меняет игровые данные.

## Хранилище и обмен данными

- SQLite с включёнными foreign keys, транзакциями, явной версией схемы и последовательными миграциями.
- Репозитории предоставляют операции доменного уровня; UI не формирует SQL.
- Таблица `local_selection_items` хранит одну подборку без именованных наборов.
- При миграции единственный старый профиль переносится в подборку; несколько старых профилей сохраняются нетронутыми в legacy-таблицах, подборка остаётся пустой во избежание неоднозначного слияния.
- Backup экспортирует только consistent SQLite snapshot приложения в ZIP: manifest фиксирует версии приложения/схемы, время, размер и SHA-256 базы. Restore preview проверяет состав архива, checksum, целостность SQLite и foreign keys, показывает число каталожных записей/элементов подборки/избранного/legacy profiles и требует подтверждения. Перед заменой live connection создаётся временная safety-копия для отката. Архивы несовместимой схемы не восстанавливаются; настройки, журналы и любые файлы Steam/Dota исключены.

## Кроссплатформенный интерфейс

- `pathlib.Path` и явные адаптеры для платформенных путей; UI и домен не проверяют `sys.platform`.
- Linux использует XDG data/config/cache каталоги; Windows — пользовательские каталоги данных через Qt QStandardPaths либо адаптер конфигурации.
- Steam libraries определяются из известных пользовательских конфигурационных файлов и проверяемых стандартных мест; путь можно задать вручную.
- Symlink-пути нормализуются и проверяются до доступа; протокол не следует по ссылке за пределы разрешённой области поиска.
- Нативная установка и Proton представлены разными вариантами обнаружения, но оба остаются read-only.

## UI и стиль

Оригинальные виджеты Qt Widgets, тёмная нейтральная палитра и умеренные розовые акценты. Каталоги выводятся через `QAbstractItemModel`/`QSortFilterProxyModel` и постраничную либо ленивую загрузку, а не отдельный виджет на каждый предмет. Контраст, фокус клавиатуры, масштабирование и строки разной длины учитываются в базовой верстке.
